# 组件命名补充说明

本文件是 [Naming_Rules.md](Naming_Rules.md) 的补充说明，不替代主规范。

## 1. 文档分工

- `Naming_Rules.md` 只负责 4 个核心字段和基础命名语法。
- `Naming_Component_Notes.md` 负责全部执行类说明，也是本项目 Figma 可见名称与写回格式的唯一操作说明入口。

执行类说明包括：

- 不命名范围
- `COMPONENT_SET` 处理规则
- 父组件内部实现层处理规则
- 全量 `INSTANCE` 候选、写回后回扫和零残留校验
- 用户可见名称展示规则
- `属性名=` 处理规则
- 自动修正和人工确认边界
- 冲突报告输出方式
- 写回 Figma 时的保护规则

如果未来再有流程、确认机制、报告样式、用户输出口径或执行口径变化，默认加到本文件，不改 `Naming_Rules.md`。

如果两份文档对“Figma 最终可见名称”或“写回格式”的表述不完全一致，以本文件为准。

### 1.1 全局命名优先级

命名在保证 `component_id` 唯一、业务语义明确、变体可区分、长期稳定的前提下，尽量简洁。

执行时应优先删除无意义重复，而不是压缩到难以理解：

- 可以省略重复页面、重复父级、重复状态文案
- 不要为了变短而使用模糊词，例如“标题”“标签”“图标”
- 不要为了变短而牺牲 AI 检索、人工阅读或跨页面复用
- 如果“简洁”和“语义明确”冲突，优先保证语义明确

### 1.2 `COMMON` / `FOUNDATION` 执行口径

当前默认执行逻辑不变，仍优先按原页面或场景生成 `page_id`，例如 `HOME`、`LIST`、`DETAIL`。

只有在命名时用户明确说明目标属于共享域时，才允许使用共享域字段代替页面型 `page_id`：

- `COMMON`：跨页面复用的业务组件
- `FOUNDATION`：基础资产，如 `icon`、`divider`、`mask`、`bg`

执行要求：

- 不要因为节点“看起来像公共组件”就自动改用 `COMMON` 或 `FOUNDATION`
- 用户没有明确说明时，继续沿用原先 page-based 命名逻辑
- 公共基础资产的默认跳过、纳入命名与确认边界，仍按本文件 `4.6 公共基础资产排除规则` 执行
- 只有在用户明确要求使用 `COMMON` 或 `FOUNDATION` 时，才把这个字段写入 `page_id`，并同步作为 `component_id` 第一段

## 2. 不命名范围

- 不给纯文本命名
- 不给最外层分区命名，即页面第一层 frame
- 不给 `COMPONENT_SET` 命名

如果某个文本内容具有业务语义，但当前节点只是原始文字层，则命名承载该语义的最小可复用非文本容器，不直接命名文字层本身。

## 3. `COMPONENT_SET` 处理规则

- `COMPONENT_SET` 只作为变体结构容器读取，不是命名或改名目标。
- 命名时只处理其下面真正承担变体值的子 `COMPONENT`。
- 如果 `COMPONENT_SET` 名称本身不规范，也不要直接修改它；记录为跳过项即可。
- 如果需要对用户说明这类节点，应该明确说它是“变体容器”或“变体结构节点”，不是最终命名目标。

## 4. 父组件内部实现层处理规则

本项目默认不定义“槽位”概念。

执行时不要因为某个节点位于父组件内部，就把它默认降级成“槽位”“容器”或“承载区”。

如果父组件内部某一层明显对应一个独立组件的实现形态，应直接把它视为该组件，纳入同名检查、标准命名生成、自动修正和冲突确认流程。

### 4.1 纳入同名检查的条件

以下情况应纳入同名检查：

- 父组件内部这层本身就是一个完整、可辨识的业务组件
- 它与页面里某个独立组件在视觉结构上明显一致
- 它与独立组件承担同一业务语义，而不是纯排版包裹关系
- 当前层已经是承载该语义的最小可复用非文本容器

### 4.2 命名要求

- 这类节点直接命名成对应组件的完整名称，不要为了区分父子层级额外发明“槽位名”
- 如果它和独立组件是同一组件的不同状态，继续使用同一个 `component_id`，再用 `#variant_id` 区分
- 如果它是 Figma 变体子组件，仍按本文件的 `属性名=` 保护规则写回

### 4.3 不纳入同名检查的层

以下层不要当作组件本体纳入同名检查：

- 纯排版包裹层
- 只负责定位、裁切、占位、对齐的外层容器
- 背景层、蒙层、描边层、阴影层等视觉辅助层
- 还不是最小可复用单元的更大组合层

### 4.4 判定原则

- 不按“它是不是在父组件里面”决定是否同名
- 按“它是不是那个组件本体”决定是否同名
- 只要明显对应独立组件，就直接按同一组件处理

### 4.5 父组件内的变体实例补判

有一类节点容易漏判：

- 它位于父组件内部
- 它的名字只写到基础组件名，没有写出 `=变体值`
- 但它实际上承载的是某个具体变体实例，和页面里其它地方的同一组件家族有关
- 或者它本身是 `INSTANCE`，Figma 原始 `name` 只保留了组件基础名，而所选变体值实际存放在 `componentProperties` 或 `mainComponent` 上

这类节点不能因为名字“看起来像容器”就直接跳过，必须先按视觉和归属组件家族归一化，再决定是否自动修正或进入用户确认。

处理原则：

- 对 `INSTANCE`，不要只看原始 `instance.name`；必须同时读取它当前指向的 `mainComponent` 和所选 `componentProperties`
- 如果 `INSTANCE` 指向的是某个 `COMPONENT_SET` 子变体，比较时要先还原成“基础组件名 + 当前变体值”的完整语义
- 如果能从视觉状态明确推断出它对应的具体变体，直接补全到完整名称
- 如果不能明确推断，放入待确认冲突组，不要静默跳过
- 不要把“只写了基础组件名”误当成“无需处理的普通包裹层”

### 4.5.1 全量 INSTANCE 候选硬约束

目标 page 或目标区域内的所有 `INSTANCE` 都是默认候选，必须全量扫描。

执行时必须包括：

- 独立摆放在页面上的 `INSTANCE`
- 嵌套在 `COMPONENT` 内部的 `INSTANCE`
- 嵌套在另一个 `INSTANCE` 内部、能被 Figma MCP 读取到的实例子节点
- 完整页面示例、组合组件、父组件变体内部引用的 `INSTANCE`

对每个 `INSTANCE`，必须读取：

- `instance.name`
- `getMainComponentAsync()` 返回的 `mainComponent.name`
- 如果 `mainComponent` 属于 `COMPONENT_SET`，还要读取其父 `COMPONENT_SET` 名称
- `instance.componentProperties`

执行时不得只依赖 `instance.name` 判断是否需要处理。只要 `mainComponent.name` 已经是标准完整名称，或 `componentProperties` 能明确还原当前变体语义，即使 `instance.name` 只写了基础组件名，也必须纳入自动修正队列。

典型必须处理的情况：

```text
instance.name: 信息区/标题区
mainComponent.name: 信息区/标题区=单行标题｜DETAIL.INFO_SECTION.TITLE_AREA#SINGLE_LINE_TITLE
```

这种情况属于实例名未同步，不是人工确认冲突；必须直接自动修正为：

```text
信息区/标题区=单行标题｜DETAIL.INFO_SECTION.TITLE_AREA#SINGLE_LINE_TITLE
```

禁止因为该 `INSTANCE` 位于父组件内部、完整页面示例内部、或看起来像“基础容器名”，就跳过这一轮判断。

### 4.5.2 写回后的 INSTANCE 回扫门

每次写回 `COMPONENT` 名称后，必须立即执行一次全量 `INSTANCE` 回扫。

回扫规则：

- 扫描目标 page 或目标区域内所有 `INSTANCE`
- 对每个 `INSTANCE` 重新读取 `mainComponent.name` 和 `componentProperties`
- 如果 `mainComponent.name` 已经是标准完整名称，且当前 `instance.name` 不是该实例当前语义对应的完整名称，必须自动修正 `instance.name`
- 如果 `mainComponent` 是远程只读组件，不能修改主组件定义名时，仍然必须尽量修正当前文件中可写的 `INSTANCE` 名称
- 如果某个 `INSTANCE` 因远程只读、Figma 限制或节点不可写导致不能修正，必须列入跳过清单，并给出完整名称和原因

这一步是收尾前必过门槛，不是可选优化。没有执行 `INSTANCE` 回扫，不允许宣称命名任务完成。

### 4.5.3 零残留校验门

最终输出前必须执行零残留校验。

校验规则：

- 再次扫描目标 page 或目标区域内所有 `INSTANCE`
- 对所有能从 `mainComponent.name` 或 `componentProperties` 明确还原标准完整名称的 `INSTANCE`，检查 `instance.name` 是否已同步为标准完整名称
- 如果仍存在未同步 `INSTANCE`，必须继续修正
- 如果因为只读或 API 限制无法修正，必须作为阻塞/跳过项明确列出
- 不允许在存在未同步 `INSTANCE` 且未说明原因时，输出“无待确认冲突”或“已完成”

最终结果说明里必须包含：

- 已回扫 `INSTANCE` 数量
- 已自动同步 `INSTANCE` 数量
- 未同步残留数量
- 未同步残留清单；如果为 0，明确写“未同步 INSTANCE 残留：0”

### 4.6 公共基础资产排除规则

有一类节点虽然位于父组件内部，也可能被写成 `模块/图标=状态` 这类名字，但它本质上不是当前页面要单独命名的业务组件，而只是公共基础视觉资产。

这类节点默认跳过，不纳入当前页面组件命名、同名检查、自动修正冲突确认或 HTML 报告。

默认跳过的典型类型：

- 通用 icon、箭头、返回符、收藏符、定位符、播放符等基础图标
- 分割线、描边、底板、背景片、蒙层、阴影片等视觉辅助层
- 只为父组件服务的局部视觉元素，即使它在当前父组件里看起来像一个独立小层级

判定原则：

- 如果一个节点离开当前父组件后，不足以单独表达业务语义，默认跳过
- 如果它更像“父组件内部用到的公共资产”，而不是“当前页面独有的业务组件”，默认跳过
- 不因为它长得一致、名称里带有 `图标`、或被包成一个小容器，就自动把它纳入冲突确认

典型例子：

- `底部导航/Tab=我的收藏｜HOME.BOTTOM_NAV.TAB#FAVORITES` 是业务组件，应纳入命名
- `底部导航/图标=收藏｜HOME.BOTTOM_NAV.ICON#FAVORITES` 默认视为 Tab 内部使用的公共 icon，不单独作为当前页面组件命名目标

只有满足以下任一条件时，这类 icon 或小型视觉节点才纳入命名与确认：

- 它本身就是一个独立可复用的业务组件，而不只是视觉素材
- 它的不同状态或变体本身承载明确业务语义
- 页面中确实把它当作独立组件体系在使用，而不是父组件的内部素材

如果不能明确判断，优先跳过并记入跳过清单，不要直接拉进用户确认报告。

## 5. 用户可见名称展示规则

当 AI 告诉用户“这个组件叫什么”“当前名称是什么”“建议改成什么”“已修正为什么”时，必须使用完整名称，不要只说中文，不要只说英文。

这条规则适用于所有用户可见输出，不只限于卡片字段。也就是说，以下场景也必须使用完整名称：

- 回复正文里的组件名
- 自动修正清单
- 跳过清单
- 待确认冲突组清单
- HTML 报告标题
- HTML 报告副标题里引用到的候选组件名

绝对不要只输出裸 `component_id`、裸 `variant_id` 或只输出中文简称来代替组件名称。

完整名称规则：

- 无变体：`display_name｜component_id`
- 有变体：`display_name=中文变体｜component_id#variant_id`
- Figma 变体子组件对用户展示时：`属性名=中文变体｜component_id#variant_id`

示例：

```text
酒店卡片/图片区｜LIST.HOTEL_CARD.IMAGE_AREA
搜索模块/搜索按钮=常规按钮｜HOME.SEARCH_MODULE.SEARCH_BUTTON#DEFAULT
搜索模块/Tab切换区=国内｜HOME.SEARCH_MODULE.TAB_SWITCH#DOMESTIC
```

补充要求：

- 如果节点是 Figma 变体子组件，`属性名=` 左侧字段就是 Figma 原生变体属性名，也承担中文组件基名。
- 对这类节点，用户侧完整名称可以展示为 `属性名=中文变体｜component_id#variant_id`，不要再把完整 `display_name` 重复写到 `=` 右侧。
- 真正写回 Figma 时，完整名称仍然直接写在 `name` 里，但 machine side 的状态分隔符必须使用 `#`，不能再写成第二个 `=`。
- 如果当前名称不完整，但 AI 已经能判断标准名，则输出时同时给出“当前名称”和“建议标准名称”，两者都按用户可见完整名称规则展示。

## 6. `属性名=` 处理规则

这里的 `属性名=` 指 Figma 变体识别用的左侧属性前缀，例如：

```text
搜索模块/Tab切换区=国内｜HOME.SEARCH_MODULE.TAB_SWITCH#DOMESTIC
```

### 6.1 Figma 官方术语对应关系

在 Figma 官方语义里，这里涉及 3 个概念：

- `Component set`：一组 `Variants` 共同所属的组件集
- `Property name`：Figma 变体名里 `=` 左侧字段
- `Value`：Figma 变体名里 `=` 右侧字段

本项目对这 3 个概念的理解和标准生成规则如下：

- 先确定一组 `Variants` 所属的 `Component set` 语义名称
- 每个变体子组件左侧的 `Property name`，应与该 `Component set` 的语义名称保持一致
- 右侧的 `Value` 只表达该变体的具体状态或取值，不再重复组件基名

示例：

```text
猜你喜欢/酒店卡片/标题区=常规｜HOME.RECOMMENDED.HOTEL_CARD.TITLE_AREA#DEFAULT
猜你喜欢/酒店卡片/标题区=换行打点｜HOME.RECOMMENDED.HOTEL_CARD.TITLE_AREA#WRAP_TRUNCATED
```

这意味着：

- `猜你喜欢/酒店卡片/标题区` 是该组 `Variants` 共享的 `Component set` 语义名称
- `猜你喜欢/酒店卡片/标题区` 同时也是变体子组件左侧的 `Property name`
- `常规`、`换行打点` 是右侧的 `Value`

这条规则不仅用于 AI 理解和人工审查，也用于本 skill 的默认标准命名生成。

也就是说：

- 当 `Component set` 共享名与子 `Variant` 左侧 `Property name` 一致时，按现状继续保留
- 当两者不一致时，这本身就是命名不规范，需要纳入自动修正

这里的“修正 `Property name`”不是随意改写左侧字段，而是把子 `Variant` 的左侧字段对齐到其所属 `Component set` 的共享语义名。

执行时必须遵守：

- 不允许脱离 `Component set` 语义上下文，随意删除、翻译、改写或标准化 `属性名=` 左侧字段。
- 对 Figma 变体子组件，`属性名=` 左侧字段保留为中文组件基名，中文侧继续用 `=` 表达变体值。
- 如果发现同一组 `Variants` 的 `Component set` 共享名与子 `Variant` 左侧 `Property name` 不一致，应以 `Component set` 共享名为准，整体修正这一组子 `Variant` 的左侧字段。
- 命名分析、冲突分组和 `display_name` 提取时，应该把 `属性名=中文变体` 还原为完整 `display_name=中文变体` 语义。
- 当前名称展示、建议标准名称展示、截图说明、HTML 报告文案中，可以展示 `属性名=中文变体｜component_id#variant_id` 这个完整短名称。
- 如果两个节点的差异发生在 `属性名=` 左侧字段，先判断它是否会影响用户可见完整名称；会影响时按命名不一致处理，不要简单忽略。
- 如果只是单个节点左侧字段与该组 `Component set` 不一致，这属于结构化命名问题，默认直接自动修正，不进入用户确认。
- 如果用户未来要求把整个 `Component set` 本身改名，或要求把一整套共享语义从 A 迁移到 B，这属于更高层级的命名变更，再由用户确认后整体调整。

## 7. 自动修正和人工确认的分界

先把节点名称清洗成统一语义后再做判断。普通节点按 `display_name=中文变体｜component_id#variant_id` 解析；Figma 变体子组件按 `属性名=中文变体｜component_id#variant_id` 解析，并把 `属性名=中文变体` 还原为完整 `display_name=中文变体` 语义。

### 7.1 直接自动修正，不需要用户确认

以下情况都属于机器字段问题：

- `display_name` 相同，只是 `｜` 右侧的 `component_id` 或 `variant_id` 不同
- 一个节点已经带完整 machine id，另一个节点缺少 machine id
- 英文 `component_id` 或 `variant_id` 缺失、错误、大小写不规范、分隔符不规范
- 状态只写在 `display_name` 里，但应该同步表达为 `variant_id`
- 出现 `##`、错误层级分隔等明显格式问题，且意图明确
- 同一组 `Variants` 的 `Component set` 共享名与子 `Variant` 左侧 `Property name` 不一致
- `INSTANCE` 指向的 `mainComponent.name` 已经是标准完整名称，但 `instance.name` 仍是基础组件名、旧名称或缺少 `variant_id` / machine id
- `INSTANCE` 的 `componentProperties` 已经能明确给出当前变体值，可还原为标准完整名称

这类问题 AI 直接修正，不进入用户确认。  
关键前提：

- 自动修正之前，必须先检查 `component_id` 唯一性。
- 一个 `component_id` 只能代表一个组件身份。
- 同一组件的不同状态，用 `variant_id` 区分；不同组件，用不同 `component_id` 区分。

补充说明：

- 如果一个节点在父组件内部，另一个节点是独立组件定义，只要两者明显是同一组件，也按这里的机器字段规则直接修正或统一，不因为层级不同而跳过。
- 如果一个 `INSTANCE` 的 `mainComponent.name` 已经能明确还原为某个标准完整名称，不要把它放入 HTML 冲突报告要求用户判断；这属于实例同步问题，必须自动修正或列入不可写跳过项。

### 7.2 需要用户确认

只有同时满足以下条件，才需要用户确认：

- 视觉完全一致
- 可见文字完全一致
- 清洗后的 `display_name` 本身不同

也就是说：

- 如果 `display_name` 相同，只是 `component_id#variant_id` 不同，不问用户，直接同意并修正。
- 只有 `display_name` 不同时，才向用户确认是否是同一个组件。
- 如果某个父组件内部实现层只写了基础组件名，没有写出 `=变体值`，不要因为它看起来像“容器”就跳过；先把它归入对应组件家族，再按上面的确认条件判断。
- 如果这个节点是 `INSTANCE`，且它的原始 `name` 只是组件基础名，而 `componentProperties` 已经明确给出了当前变体值，也不能跳过；要先按“完整语义名”参与比较。

### 7.3 不进入“是否同一组件”确认的问题

以下情况不要问用户“是不是同一个组件”：

- 样式、布局、尺寸、子结构不同
- 可见文字不同
- 明显是不同状态、不同取值、不同布局条件
- 只是一个在父组件内部、另一个是独立组件定义，但清洗后的 `display_name` 相同
- 明显只是父组件内部使用的公共基础资产，例如通用 icon、箭头、背景片、分割线等

这类问题优先按不同 `variant_id` 或不同 `component_id` 处理。

## 8. 用户确认闭环

当且仅当存在“视觉完全一致且 `display_name` 不同”的冲突组时，才发起用户确认。

标准闭环：

1. AI 先检索并聚合疑似同一组件的节点
2. AI 生成一份 HTML 冲突报告
3. 用户确认这些节点是否是同一个组件
4. 如果用户确认是同一个组件，用户只提供统一后的中文 `display_name`
5. 系统再自动修正整组节点的命名

不要让用户处理机器字段问题。机器字段问题由 AI 自行修正。

## 9. HTML 冲突报告规则

### 9.1 输出方式

- 不要把确认内容写到 Figma 画板里。
- 直接输出一份 HTML 报告。
- 单次执行只允许产出一份 HTML 报告。
- 如果有多个冲突组，按纵向顺序向下增加，放在同一份报告里，不要拆成多份。

建议默认文件名：

```text
figma-naming-conflicts-report.html
```

如果用户任务有明确页面名，也可以用更具体的文件名，但仍然只能产出一份报告。

### 9.2 适用范围

- 只有“视觉完全一致且 `display_name` 不同”的冲突组需要进 HTML 报告。
- 如果 `display_name` 相同，只是 `component_id#variant_id` 不同，这类问题不要进 HTML 报告，直接自动修正。
- 如果一个在父组件内部、另一个是独立组件定义，但两者清洗后的 `display_name` 相同，也不要进 HTML 报告。
- 如果节点本质上只是父组件内部使用的公共基础资产，例如通用 icon、箭头、背景片、分割线等，也不要进 HTML 报告。

### 9.3 样式来源

HTML 报告样式参考以下 Figma MCP 节点：

```text
https://www.figma.com/design/2CXckWUEm1b8tpa3v7SG1M/%E9%85%92%E5%BA%97-AI-Design-Context?node-id=706-2035&t=7JNwYwGFy8aOLHdT-4
fileKey: 2CXckWUEm1b8tpa3v7SG1M
nodeId: 706:2035
```

说明：

- 旧配置节点 `731:3531` 当前已失效，不再作为主样式参考节点。
- 当前有效主样式参考节点为 `706:2035`。

执行要求：

- 生成 HTML 报告前，必须先实际读取这个样式参考源，至少执行一次 `get_metadata`、`get_screenshot` 或等效 Figma MCP 读取。
- 不允许在没有读取样式参考源的情况下，直接手写一份“通用卡片风格” HTML 代替。
- 如果上面的固定 `nodeId` 已失效，必须先在同一 Figma 文件里搜索当前仍存在的样式参考节点，再继续生成 HTML。
- 当前推荐的回退搜索目标是命名中包含 `命名冲突确认板`、`冲突组`、`当前名称` 的现存节点，并优先使用同一主题下最新、最完整的一组。
- 发生回退时，要在执行结果说明里明确告知用户：固定样式节点失效，本次使用了哪个实际节点作为样式参考。

核心结构：

- 外层白底容器
- 每个冲突组纵向堆叠
- 每组包含标题、副标题、证据卡片区
- 多个问题一直向下追加

视觉要求：

- 版式、层级、留白节奏要尽量贴近样式参考节点，不要自行发挥成另一套视觉语言。
- 优先复用参考节点里已经存在的结构关系，例如：标题区、`DISPLAY_NAME` 副标题、双列证据卡、浅灰证据卡底、卡片内截图标题与文字说明的顺序。
- 如果因为 HTML 的响应式限制无法 1:1 复刻，也要优先保持“整体观感相近”，而不是只保留抽象结构。

### 9.4 标题和副标题

- 标题格式：`冲突组 {序号}: {完整名称A} / {完整名称B}`
- 副标题格式：`display_name 基名：{名称A} / {名称B}`

注意：

- 标题里的组件名必须使用完整名称，不能只写英文 `component_id`
- 如果冲突组里已经有明确的建议标准名称，标题优先展示该建议标准名称；如果有两个候选名称，则用 `完整名称A / 完整名称B`
- 副标题里的基名必须基于“去掉 `属性名=` 左侧字段后”的 `display_name`
- 不要在副标题里展示 `属性名=` 左侧字段

### 9.5 证据卡片内容

每张证据卡片至少包含：

- `当前名称`
- `建议标准名称`
- `合并数量`
- `全部节点 ID`
- `冲突原因`

说明：

- `当前名称` 和 `建议标准名称` 都必须按用户可见完整名称规则展示。
- 当前这版报告默认不展示 `节点类型`。

### 9.6 证据卡片预览

- 预览必须完整展示组件全貌
- 不要固定成裁切方框
- 保持原始宽高比
- 不拉伸、不裁切
- 如果组件较宽或较高，预览区域要自适应增长
- 如果双列下仍然无法完整显示，改单列展示该卡片

目标优先级：

1. 完整显示组件
2. 信息可读
3. 排版整齐

### 9.7 报告里绝对不要展示的内容

- 破坏 Figma 变体功能的改写结果
- 写在卡片内部的红色提示话术
- “请确认是否同一组件，并给统一中文 display_name” 这类引导语

引导用户确认的话，放在 HTML 报告外的回复正文里说。

## 10. 写回 Figma 的规则

- 自动修正问题可以直接写回。
- 需要用户确认的冲突组，只有在用户确认后才写回。
- 写回前再次按 `Naming_Rules.md` 计算 `display_name`、`page_id`、`component_id`、`variant_id`。
- 如果节点是承担 Figma 变体识别职责的子 `COMPONENT`，写回格式为 `属性名=中文变体｜component_id#variant_id`。
- 绝对不要动 `属性名=` 左侧字段。
- 绝对不要重命名 `COMPONENT_SET`。
- 对 Figma 变体子组件，不要写成 `属性名=display_name=中文变体｜component_id#variant_id`。
- 父组件内部明显对应独立组件的实现层，写回时直接使用该组件的标准完整名称，不额外改写成“槽位”“容器”或其他承载类名称。
- 写回 `COMPONENT` 后，必须执行一次全量 `INSTANCE` 回扫，并把所有指向已标准命名 `mainComponent` 的可写实例同步为标准完整名称。
- 如果 `mainComponent` 是远程只读组件，不能修改主组件定义名，也不能因此跳过当前文件里的实例同步；可写 `INSTANCE` 仍必须同步。
- 写回后必须执行零残留校验；存在未同步 `INSTANCE` 时，不允许结束任务，除非这些节点已被列入跳过清单并说明不可写原因。

## 11. 每次执行后的结果说明

每次执行后都要清楚说明：

- 自动修正了哪些节点
- 写回后回扫了多少 `INSTANCE`，同步了多少 `INSTANCE`
- 未同步 `INSTANCE` 残留数量和清单
- 跳过了哪些节点
- 哪些冲突组仍待用户确认
- 如果生成了 HTML 报告，报告文件路径是什么

对用户汇报时：

- 组件名统一使用完整名称
- 如果需要列出“还有哪些冲突组待确认”，列表里的每一项也必须直接写完整名称，不允许只写英文 `component_id`
- 如果某个节点被跳过是因为它是 `COMPONENT_SET`，要明确告诉用户这是“变体容器，非命名目标”
- 如果某个节点被跳过是因为远程只读或 Figma API 不允许写入，要明确说明它不可写，但当前文件里可写的 `INSTANCE` 是否已经同步
- 如果本次没有未同步实例，必须明确写：`未同步 INSTANCE 残留：0`
